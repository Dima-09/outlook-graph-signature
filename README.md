# Outlook Graph Signature

Клиентская надстройка Outlook для автоматической вставки персональной подписи BDO.
Использует Office.js, Microsoft Graph и MSAL Browser / Nested App Authentication (NAA).
Отдельного backend нет. DEV и PROD — окружения с общей кодовой базой в ветке `main`.

## Начало работы

Нужны Node.js и npm. Для текущего lockfile рекомендуется Node.js 22 не ниже 22.15.0:
это минимальная версия для `rechoir@1.0.0`. Зависимости устанавливаются по lockfile
без автоматического обновления:

```sh
npm ci
```

| Команда | Результат |
| --- | --- |
| `npm run build:dev` | Комплект DEV в `dist/dev/` |
| `npm run build:prod` | Комплект PROD в `dist/prod/` |
| `npm run build:all` | Последовательная сборка DEV, затем PROD |
| `npm test` | Офлайн-проверки сборщика и сохранения поведения подписи |

Если PowerShell блокирует `npm.ps1`, используйте `npm.cmd` вместо `npm`.
Сборщик использует Node API Webpack. Локальный HTTPS-сервер и вход в Microsoft 365
для компиляции не нужны. Обе среды собираются с Webpack `mode: 'production'`:
имя окружения DEV не означает режим разработки Webpack.

Сборка ничего не публикует. `dist/` и `node_modules/` исключены из Git.
Существующий каталог `dev/` и старые корневые ресурсы обслуживают GitHub Pages
и сохраняются без изменений до завершения миграции. Новые сборки используют
`src/`, `public/`, `config/` и `manifests/`.

## Настройки окружений

Источники параметров — `config/dev.json` и `config/prod.json`.

| Поле | Контракт сборщика |
| --- | --- |
| `configured` | Обязательное boolean; `false` отмечает незавершённую настройку |
| `baseUrl` | Абсолютный HTTPS URL без credentials, query, fragment, пробелов и обратных слешей; подкаталог допустим |
| `clientId` | UUID регистрации Entra ID |
| `authority` | HTTPS URL с единственным сегментом пути — UUID tenant; host `login.microsoftonline.com` или тестовый `.invalid` |
| `addinId` | Постоянный UUID надстройки Outlook, отдельный от Client ID |
| `displayName` | Непустое название надстройки |
| `manifestVersion` | Четыре числовых компонента в диапазоне 0–65535 |

Неизвестные поля, включая `outputDir`, отклоняются. Строки не допускают внешних
пробелов, незаменённых шаблонных маркеров и недопустимых XML-символов. Завершающий
слеш `baseUrl` нормализуется. Локальный путь вывода определяется только target
`dev` или `prod`, а публичные URL вычисляются отдельно.

Текущее состояние конфигураций:

- DEV: `baseUrl` равен `https://outlook-signature-dev.bdoqz.workers.dev/`;
  сохранены идентификаторы прежнего DEV и версия манифеста `1.0.0.5`.
- PROD: `baseUrl` равен `https://signature-prod.example.invalid/`;
  Client ID и authority содержат явные тестовые значения. Отдельный постоянный
  `addinId` уже записан в конфигурации, версия манифеста — `1.0.0.0`.
- У обеих сред `configured: false`. Наличие DEV URL в файле не подтверждает
  публикацию, настройку Entra или работоспособность надстройки.

При `configured: false` корректная по форме конфигурация компилируется с предупреждением
**`NOT CONFIGURED — DO NOT DEPLOY`**. Такие артефакты не считаются релизом.
При `configured: true` сборщик дополнительно отклоняет `.invalid` URL и известные
тестовые UUID. Проверка формата не подтверждает готовность внешних систем:
даже успешная сборка выводит `CONFIGURED (deployment not verified)`.
Флаг не меняет поведение авторизации и не блокирует публикацию внешними средствами.

Client ID и Tenant ID — публичные идентификаторы. Client Secret приложению не нужен.
Версия манифеста и GUID не изменяются автоматически при сборке.

## Локальные проверки и их пределы

`npm test` содержит проверки конфигурации, XML/JSON, изоляции выходных папок,
сохранения результатов при ошибках, блокировок, защиты от junction, числа чанков
и подписи на фиктивных данных. Тесты сборщика используют подставной компилятор;
они не заменяют настоящую компиляцию. Временные тестовые каталоги создаются
в `dist/.test-*` и удаляются после проверки.

**Известное расхождение:** в `tests/build.test.cjs` набор ошибочных значений включает
`{ configured: true }` поверх текущего DEV. После замены DEV URL на `workers.dev`
эта конфигурация проходит существующую валидацию, поэтому ожидание исключения
устарело. Это выявлено чтением кода; тест в рамках обновления документации не запускался
и не исправлялся. Также тесты привязаны к `configured: false`, прежним идентификаторам,
версии и файлам `dev/`; перед миграцией их нужно пересмотреть отдельной задачей.

Сборщик проверяет подстановки и состав ресурсов, но не содержит универсального
XML-парсера. После сборки синтаксис XML можно проверить штатным System.Xml:

```powershell
$ErrorActionPreference = 'Stop'
foreach ($target in @('dev', 'prod')) {
    $xmlPath = Join-Path (Get-Location) "dist/$target/manifest.xml"
    $xml = New-Object System.Xml.XmlDocument
    $xml.XmlResolver = $null
    $xml.Load($xmlPath)
    Write-Output "$target XML: OK"
}
```

Это не проверка схемы официальным валидатором Office Add-in и не проверка Outlook.
Критерии приёмки сборок и проверки реальной среды приведены в [REFACTORING.md](REFACTORING.md).
При изменении только документации достаточно проверки текста, ссылок и Git diff;
сборки и тесты создают файлы вне Markdown и в такую проверку не входят.

## Публикация

Выбран Cloudflare Workers Static Assets: отдельный Worker для DEV и PROD,
только статические файлы, без серверной логики Worker. Публикация выполняется
вручную и отдельно от сборки. Wrangler, Cloudflare API, интеграция с GitHub
и автоматическая публикация сейчас не используются.

Переход на Cloudflare ещё требует проверки и завершения. Действующая публикация
GitHub Pages сохраняется для старой корпоративной надстройки.
Порядок перехода и условия последующей очистки — в [REFACTORING.md](REFACTORING.md).
