# AGENTS.md — правила работы с Outlook Graph Signature

## Назначение проекта

Корпоративная надстройка Outlook для автоматической вставки персональной подписи BDO. Использует Office.js, Microsoft Graph, Microsoft Entra ID, MSAL Browser (Nested App Authentication, NAA) и Webpack. Это клиентское статическое приложение, отдельный backend сейчас не нужен.

Язык общения, планов и отчётов — русский. Существующие англоязычные идентификаторы, тексты подписи и стиль исходников сохранять. Не переводить программный код и содержимое подписи без задания.

## Архитектурные правила

- Один репозиторий, одна постоянная ветка `main` на текущем этапе. Не создавать `develop`, `dev`, `gh-pages` и другие ветки самостоятельно. Возможное разделение веток в будущем не должно требовать изменения модели сборки.
- Один набор общих исходников. DEV и PROD — среды сборки, а не две копии исходного кода или две ветки.
- Команды `npm run build:dev` и `npm run build:prod` формируют соответственно `dist/dev/` и `dist/prod/`. `npm run build:all` собирает обе среды. Сборка одной среды не меняет файлы другой.
- Настройки, зависящие от среды, хранить в отдельных конфигурациях; общий код и общий шаблон манифеста не дублировать. Пути на диске и публичные URL — разные понятия.
- Сборка и публикация — отдельные операции. Сборщик не должен загружать файлы на хостинг, менять Entra ID или Microsoft 365. GitHub используется для исходников; в будущем планируются два проекта Cloudflare Pages. Публикация ручная.
- Сгенерированные файлы не редактировать вручную. `dist/` и `node_modules/` не коммитить. Исключение на период миграции — существующие опубликованные файлы GitHub Pages, которые нужно сохранить без изменений до отдельного разрешения.
- Предпочитать простые решения и существующие зависимости. Не вводить новый фреймворк, сервер, CI/CD, менеджер пакетов, дополнительные окружения или сложные абстракции без необходимости и согласования.

## Безопасные границы работы

- Перед редактированием прочитать `ARCHITECTURE.md` и `REFACTORING.md`, проверить фактический код, ветку и `git status`. Документы — контекст и требования, а не доказательство текущего состояния файлов. При расхождениях описать их владельцу.
- Сначала предоставить план, включая список перемещаемых, создаваемых, изменяемых и удаляемых файлов. Не приступать к реализации до одобрения плана.
- Не менять бизнес-логику подписи, поля Microsoft Graph, обработку ошибок, поведение авторизации, набор API-разрешений, событийный обработчик, совместимость Outlook и интерфейс без отдельного задания.
- Не редактировать сгенерированные опубликованные бандлы в `dev/`, старые корневые ресурсы, действующий манифест и отдельный репозиторий домена GitHub Pages. Не удалять их до миграции и подтверждения владельца, даже если кажутся устаревшими.
- Не выполнять `git add`, `git commit`, `git push`, создание тегов/веток, `git reset --hard`, `git clean`, `git checkout -- .`, переписывание истории и другие операции, меняющие историю, индекс или уничтожающие изменения пользователя, без явного разрешения. Не перетирать существующие незакоммиченные изменения. Разрешено читать состояние Git и diff.
- Работать в пределах открытого репозитория. Не изменять системные настройки и другие проекты. Для сетевого доступа и установки зависимостей использовать предусмотренные разрешения среды Codex.
- Не создавать и не запрашивать Client Secret для клиентского приложения. Client ID и Tenant ID — публичные идентификаторы, а не секреты. Не выводить токены, реальные профили сотрудников, персональные данные или учётные данные в тесты, отчёты и новые файлы. Не заменять отсутствующие реальные настройки вымышленными рабочими значениями.

## Качество результата

- Сохранять отдельные самодостаточные JavaScript-бандлы для событийного runtime и панели Sign in. Проверять ограничения Classic Outlook: не допускать дополнительных необходимых JS-чанков.
- Проверять обе сборки, содержание сгенерированных конфигураций, XML, `.well-known`, ссылок на ресурсы и независимость выходных папок.
- Использовать воспроизводимые проверки, по возможности без обращений к реальному Microsoft Graph и без входа в корпоративную учётную запись. Для тестовых данных использовать фиктивных пользователей.
- Не выдавать проверку сборки за проверку работоспособности установленной надстройки. Outlook Classic, New, Web и Mobile требуют отдельной проверки в реальной среде.
- В конце сообщить: какие файлы изменены, что удалено и почему, какие команды выполнены, какие проверки прошли или не прошли, что осталось неизвестным, какие действия потребуются от владельца. Показать `git status` и краткий diff. Не делать commit/push/deploy.
