# Outlook Graph Signature

Клиентская надстройка Outlook для персональной подписи BDO: Office.js,
Microsoft Graph и MSAL Browser / Nested App Authentication. Backend не требуется.
DEV и PROD собираются из общих исходников в ветке `main`. Сборка ничего не публикует.

## Структура

| Путь | Назначение |
| --- | --- |
| `src/` | Общие исходники событийного runtime, Sign in, авторизации и подписи |
| `config/dev.json`, `config/prod.json` | Публичные параметры сред |
| `public/` | Общие HTML и иконки |
| `manifests/manifest.template.xml` | Единый шаблон на основе действующего DEV-манифеста |
| `webpack.config.js` | Фабрика конфига для каждой из двух независимых компиляций |
| `scripts/build.cjs` | Проверка конфигурации, компиляция, сборка комплекта и замена результата |
| `tests/` | Офлайн-проверки сборщика и сохранения поведения подписи |
| `dist/dev/`, `dist/prod/` | Генерируемые комплекты, исключённые из Git |

**Существующий `dev/` и корневые `manifest.xml`, `commands.html`, `commands.js`,
`icon-*.png` заморожены до отдельной миграции.** Они обслуживают прежнюю публикацию
GitHub Pages. Новая сборка их не читает как исходники и не перезаписывает.
Тесты используют эти файлы как контрольную версию для структурного рефакторинга.
Дальнейшая разработка ведётся в `src/`, `public/`, `config/`, `manifests/`.

`public/commands.html` сохраняется для `SupportUrl` и `FormSettings`; старый
`commands.js` со статической подписью в новый комплект не включается.

## Запуск

Рекомендуется Node.js 22 версии не ниже 22.15.0 и npm. В текущем lockfile
`rechoir@1.0.0` требует Node.js >=22.15.0, хотя собственное требование webpack-cli ниже.
Не обновляйте зависимости автоматически. При необходимости установите их по lockfile:

```sh
npm ci
npm run build:dev
npm run build:prod
npm run build:all
npm test
```

Если PowerShell блокирует `npm.ps1`, используйте `npm.cmd` вместо `npm`:

```powershell
npm.cmd run build:all
npm.cmd test
```

Сборщик вызывает Node API Webpack, не webpack-cli. Старые вызовы
`webpack --config webpack.graph.config.js` больше не используются.
Локальный HTTPS-сервер и вход в Microsoft 365 для компиляции не нужны.

## Настройки сред

| Поле | Правило |
| --- | --- |
| `configured` | Boolean: `false` для незавершённой настройки; `true` — только после внесения реальных значений |
| `baseUrl` | HTTPS URL приложения, без credentials, query и fragment; подкаталог допустим |
| `clientId` | UUID регистрации Entra соответствующей среды |
| `authority` | `https://login.microsoftonline.com/<tenant-uuid>`; для тестов допустим `.invalid` host |
| `addinId` | Постоянный UUID надстройки Outlook; отличается от Entra Client ID |
| `displayName` | Название надстройки в манифесте |
| `manifestVersion` | Четыре числовых компонента, каждый от 0 до 65535 |

Настройки не содержат секретов. Client Secret не нужен. Произвольный `outputDir`
не поддерживается: выход определяется только аргументом `dev` или `prod`.
URL формируются через `URL`, а не через файловые функции.

Начальный DEV сохраняет Client ID, authority, GUID и версию `1.0.0.5` из прежних
исходников. Его новый `baseUrl` — `https://signature-dev.example.invalid/`.
PROD использует `https://signature-prod.example.invalid/`, тестовый Client ID
`11111111-1111-4111-8111-111111111111` и тестовую authority
`https://login.example.invalid/22222222-2222-4222-8222-222222222222`.
Постоянный GUID новой PROD-надстройки — `d59909a2-fdfd-463d-a995-b5462afaadb3`,
начальная версия — `1.0.0.0`. Сборщик не генерирует этот GUID заново.

Обе начальные конфигурации имеют `configured: false`. Обычные команды успешно
компилируют их, но печатают **`NOT CONFIGURED — DO NOT DEPLOY`**. Это проверочные
артефакты, не релиз. `configured: true` с `.invalid` или известными тестовыми UUID
отклоняется; корректный формат реальных значений сам по себе не доказывает, что
регистрация, разрешения и сайт настроены. Флаг не управляет логикой авторизации.

Версия манифеста не повышается автоматически. При миграции изменение настроек
и версии должно сопровождаться пересмотром проверок, сравнивающих их с legacy.

## Что делает сборщик

1. Проверяет target, JSON и маркеры XML до изменения результата.
2. Создаёт временную папку внутри `dist/` и блокировку выбранной среды.
3. Последовательно компилирует `graph-runtime.js` и `signin.js` из `src/`.
   `DefinePlugin` безопасно встраивает Client ID и authority в оба бандла.
4. Копирует HTML/PNG, подставляет экранированные значения в XML и формирует JSON
   с точным URL JavaScript runtime из манифеста.
5. Проверяет состав комплекта, конфигурацию и статистику чанков.
6. Заменяет только выбранную папку. До успешной компиляции и проверок прежний
   результат остаётся на месте; при ошибке установки новой папки восстанавливается
   резервная. Ошибки завершаются ненулевым кодом.

Каждый бандл имеет собственный runtime: `splitChunks: false`, `runtimeChunk: false`,
`maxChunks: 1` отдельно для каждой компиляции. Предупреждения Webpack о размере
бандлов выводятся, но не являются ошибкой сборки. Рекомендацию Webpack включить
lazy loading здесь применять нельзя без отдельной проверки событийного runtime.
Лицензионные файлы сохраняются. Office.js остаётся внешним API хоста/CDN.

Комплект каждой среды:

```text
dist/<target>/
├── .well-known/microsoft-officeaddins-allowed.json
├── manifest.xml
├── graph-runtime.html
├── graph-runtime.js
├── graph-runtime.js.LICENSE.txt
├── signin.html
├── signin.js
├── signin.js.LICENSE.txt
├── commands.html
├── icon-16.png
├── icon-32.png
└── icon-80.png
```

Две разные среды можно собирать независимо. Повторный одновременный запуск одной
среды отклоняется. После аварийного завершения процесса может остаться
`dist/.lock-dev` или `dist/.lock-prod`: перед ручным удалением убедитесь, что сборщик
больше не работает. При прерывании непосредственно во время замены также проверьте
собственную `.backup-<target>-…` папку внутри `dist/`; она содержит прежний результат.
Сборщик отказывается работать через ссылки/junction в выходных каталогах.

## Проверки

`npm test` проверяет валидацию, генерацию XML/JSON, изоляцию каталогов, сохранение
результатов при ошибках, блокировки, защиту от junction, число чанков и неизменность
подписи на фиктивных данных. Сценарии ошибок сборщика используют подставной компилятор;
они не заменяют реальные `build:dev`, `build:prod`, `build:all`.
Временные тестовые файлы создаются только в `dist/.test-*` и удаляются после проверки.

Для проверки XML штатным System.Xml после реальной сборки выполните из корня
репозитория в PowerShell (ошибки XML не подавляются):

```powershell
$ErrorActionPreference = 'Stop'
foreach ($target in @('dev', 'prod')) {
    $xmlPath = Join-Path (Get-Location) "dist/$target/manifest.xml"
    $xml = New-Object System.Xml.XmlDocument
    $xml.XmlResolver = $null
    $xml.Load($xmlPath)
    Write-Output "$target XML: OK"
}
```

Сборщик подставляет значения в известный шаблон и проверяет маркеры/ресурсы,
но не содержит универсального XML-парсера. Проверка через System.Xml подтверждает
синтаксис; это не проверка схемы Office Add-in официальным валидатором.
После структурного изменения XML выполните её заново.

При приёмке сравните SHA-256 и перечни файлов PROD до/после `build:dev`, затем DEV
до/после `build:prod`. Проверьте неизменность старого `dev/`, корневых ресурсов и
`package-lock.json`, а также `git status`, `git diff` и `git check-ignore dist/dev/manifest.xml`.
Сборки и офлайн-тесты не подтверждают работу установленной надстройки в Outlook.

## Публикация и миграция — отдельный этап

1. Владелец создаёт два отдельных сайта Cloudflare Pages и определяет их HTTPS URL.
2. Настраивает отдельную PROD-регистрацию Entra, redirect URI для NAA, доступ,
   разрешения и admin consent. Заменяет тестовые параметры и устанавливает
   `configured: true` только после настройки.
3. Собирает DEV и вручную публикует **содержимое** `dist/dev/` в корень DEV-сайта.
   Локальные `dist/dev` не добавляются автоматически к публичному URL.
4. Проверяет ресурсы, поведение HTML-редиректов и
   `https://<origin>/.well-known/microsoft-officeaddins-allowed.json`.
   При приложении в подкаталоге JSON всё равно размещается в корне origin;
   при общем origin нужен единый JSON с обоими разрешёнными runtime URL.
5. Согласует версию и обновляет установленный XML. Проверяет авторизацию,
   автоматическую подпись и Sign in в Classic, New, Web и Mobile Outlook.
6. После проверки DEV собирает PROD из того же состояния исходников и отдельно
   публикует его. Старые установки и ресурсы удаляются только после подтверждения
   миграции и отдельного разрешения владельца.

Сборщик не меняет GitHub Pages, отдельный репозиторий домена, Entra ID или Microsoft
365 и не выполняет commit/push/deploy. Авторизацию и реальные профили сотрудников
для локальных проверок использовать не нужно.
