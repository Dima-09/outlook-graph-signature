# Развёртывание Outlook Graph Signature

Пройдите процедуру сначала для DEV с отдельным тестовым почтовым ящиком Exchange Online. После приёмки повторите её для PROD из той же проверенной ревизии исходников.

## 1. Восстановить сведения о среде и подготовить доступ

| Что сверить | DEV в этой копии | PROD в этой копии |
| --- | --- | --- |
| Имя в Outlook | BDO Auto Signature DEV | BDO Auto Signature |
| Публичный адрес | `https://outlook-signature-dev.bdoqz.workers.dev/` | В файле указан `signature-prod.example.invalid`. Уточните адрес действующего Worker у владельца |
| Entra | Client ID и tenant в [config/dev.json](config/dev.json) | В [config/prod.json](config/prod.json) стоят тестовые значения |
| Идентичность установки | `addinId` из DEV, версия 1.0.0.5 | Отдельный `addinId` из PROD, версия 1.0.0.0 |
| Статус конфигурации | `configured: false` | `configured: false` |

Для действующей установки получите из порталов текущий XML или данные установленной версии, имя и версию Worker, домен, tenant, Client ID, redirect URI, согласия и обе группы назначения. Сопоставьте их с конфигурацией. Сохраните предыдущий рабочий комплект и XML для отката. URL и постоянные идентификаторы действующих сред меняйте только по отдельному решению владельца.

Потребуются доступ на чтение исходников GitHub (на запись — для сохранения изменений), право создавать и обновлять Workers в выбранном Cloudflare account, право регистрировать приложения в tenant и управлять их настройками. Для выдачи tenant-wide consent на делегированное User.Read подходит Application Administrator или Cloud Application Administrator. Для централизованного развёртывания Outlook проверьте полномочия администратора Exchange и право регистрации приложений в Entra по требованиям tenant. Проверьте лицензии Microsoft 365 и наличие ящика Exchange Online у пилотного пользователя. [Требования Microsoft 365](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/centralized-deployment-of-add-ins) · [Полномочия для consent](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/grant-admin-consent)

## 2. Подготовить две регистрации Entra

1. В Microsoft Entra admin center выберите нужный каталог. Откройте **App registrations → All applications** и найдите действующую регистрацию по Client ID. При восстановлении используйте существующую. При создании среды с нуля выберите **New registration**. Рекомендуемые имена — **BDO Outlook Signature Auth DEV** и **BDO Outlook Signature Auth PROD**.
2. Для внутренней корпоративной установки выберите **Accounts in this organizational directory only**. Приложение использует authority конкретного tenant. Тип уже действующей регистрации проверьте в портале.
3. На **Overview** запишите **Application (client) ID** и **Directory (tenant) ID**. В **Authentication → Add a platform → Single-page application** зарегистрируйте `brk-multihub://<имя-хоста-надстройки>`. Для DEV это `brk-multihub://outlook-signature-dev.bdoqz.workers.dev`. Для PROD подставьте подтверждённый хост. Для брокера нужен хост без пути к HTML и завершающего слеша. Репозиторий не содержит отдельных страниц для dialog fallback. При проверке Outlook Web сверьте также HTTPS SPA redirect фактически используемой страницы с требованиями Microsoft для этого клиента. [Настройка NAA](https://learn.microsoft.com/en-us/office/dev/add-ins/develop/enable-nested-app-authentication-in-your-add-in) · [Пример Microsoft для Outlook](https://learn.microsoft.com/en-us/samples/officedev/office-add-in-samples/outlook-add-in-sso-naa/)
4. Откройте **API permissions → Add a permission → Microsoft Graph → Delegated permissions → User.Read**. Если разрешение уже есть, оставьте одну запись. Для централизованного согласия выберите **Grant admin consent for …**, проверьте tenant, запрашиваемые права и статус **Granted**. Событийный runtime получает токен без интерактивного окна, поэтому заранее проверьте согласие на пилотной учётной записи. Клиенту не требуется Client Secret. [Получение профиля через Graph](https://learn.microsoft.com/en-us/graph/api/user-get) · [Выдача согласия](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/grant-admin-consent)
5. В **Enterprise applications → All applications** найдите service principal этой регистрации по Application ID. В **Properties** проверьте, разрешён ли вход. Если доступ к Graph через это приложение нужно ограничить группой, включите **Assignment required?**, выдайте admin consent и в **Users and groups → Add user/group** назначьте пилотного пользователя или группу. Проверьте доступность группового назначения по лицензии tenant. При выключенном требовании назначения доступ определяется согласием и политиками tenant. Повторите проверку в PROD со своей аудиторией. [Назначение пользователей](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/assign-user-or-group-access-portal) · [Диагностика согласия и назначений](https://learn.microsoft.com/en-us/troubleshoot/entra/entra-id/app-integration/troubleshoot-consent-issues)

## 3. Получить исходники, заполнить конфигурацию и собрать

1. Выполните клонирование и `npm ci` по [README.md](README.md). Для существующего рабочего дерева проверьте `git status`, ветку `main`, `git remote -v` и используемую ревизию `git rev-parse HEAD`. Обновляйте чистую ветку через `git pull --ff-only`.
2. Откройте JSON нужной среды. Запишите подтверждённый публичный HTTPS-адрес Worker в `baseUrl`, Application ID в `clientId` и `https://login.microsoftonline.com/<Directory-tenant-ID>` в `authority`. В `addinId` сохраняйте постоянный ID установки, в `displayName` — название в Outlook. Формат `manifestVersion` — четыре числа 0–65535. Для обновления XML увеличьте версию относительно установленной. Выходной каталог выбирает команда сборки.
3. Выставляйте `configured: true` после сверки реальных параметров среды. Сборщик допускает учебную сборку при `false` с предупреждением **NOT CONFIGURED — DO NOT DEPLOY**. Комплект с таким предупреждением не загружайте в Worker. Для новой регистрации Entra выдаёт новый Client ID. Его использование в существующей среде требует согласованной смены регистрации.
4. Выполните `npm test` и `npm run build:all`. Убедитесь, что в каждой папке есть XML, три HTML, три PNG, два JS-бандла и корневой каталог `.well-known`. Проверьте версию, ID, адреса среды и статус сборщика. Сохраните лицензии из выходной папки вместе с бандлами.
5. При выпуске изменений проверьте `git diff` и `git status`, добавьте в индекс только согласованные исходники, тесты, документацию и конфигурацию. После разрешения владельца выполните commit и push в GitHub. Запишите ревизию и версию XML. Публикация комплекта выполняется отдельно.

## 4. Вручную разместить файлы в Cloudflare

1. Откройте Cloudflare Dashboard → **Workers & Pages** в нужном аккаунте. Для существующей среды выберите Worker по имени и проверьте **Settings → Domains & Routes**. При создании используйте **Create application → Workers → Upload static files** или соответствующий пункт загрузки файлов. Для DEV ожидается имя `outlook-signature-dev` в поддомене аккаунта `bdoqz.workers.dev`. Имя PROD восстановите из рабочего адреса. Для нового аккаунта предварительно задайте доступный поддомен Workers и согласуйте итоговый origin.
2. Загрузите папку готовой среды так, чтобы `manifest.xml`, `signin.html` и `.well-known/` оказались непосредственно в корне. В предварительном списке проверьте скрытый каталог и обе лицензии. Выберите **Deploy** для целевого Worker. Запишите URL и ID опубликованной версии. Для обновления откройте тот же Worker и создайте новое размещение с полным комплектом. Серверный скрипт, привязка Git и команда сборки в Cloudflare этому проекту не требуются. [Cloudflare Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/)
3. Проверьте HTTP GET для `/manifest.xml`, `/commands.html`, `/graph-runtime.html`, `/signin.html`, обоих JS, трёх иконок и `/.well-known/microsoft-officeaddins-allowed.json`. Например, в Windows выполните `curl.exe -i https://outlook-signature-dev.bdoqz.workers.dev/.well-known/microsoft-officeaddins-allowed.json`. Сверьте статус, Content-Type и тело каждого ответа. При 3xx проверьте конечный URL и относительные ссылки из HTML. При возврате HTML по адресу JS или JSON проверьте структуру загрузки и маршрутизацию. Для отсутствующего файла ожидается 404. [Маршрутизация статических файлов](https://developers.cloudflare.com/workers/static-assets/routing/behavior/)
4. В JSON массив `allowed` должен содержать точный URL `graph-runtime.js` из ресурса `JavaScriptRuntime.Url` этого XML. JSON обслуживается из корня origin. Сравните загруженные файлы с локальным комплектом перед установкой манифеста.

## 5. Установить надстройку через Microsoft 365

1. В Microsoft 365 admin center откройте **Settings → Integrated apps → Upload custom apps**. Выберите **Office Add-in**, загрузку файла и сгенерированный `dist/dev/manifest.xml`. Сверьте показанные имя, версию и права Outlook.
2. Назначьте конкретного тестового пользователя или пилотную группу, примите требуемые разрешения и завершите развёртывание. Проверьте карточку приложения и назначения. Дождитесь распространения, перезапустите Outlook и откройте новое письмо. Повторите для PROD с его собственным XML и согласованной аудиторией. На пилотном ящике избегайте одновременного назначения двух обработчиков подписи. [Централизованное развёртывание Office](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/centralized-deployment-faq)
3. Различайте объекты по ID. Ручная **App registration** задаёт клиент MSAL. Её **Enterprise application** представляет этот клиент в tenant и хранит назначения и согласие. **Object ID** конкретного объекта нужен для администрирования. Карточка, появившаяся при загрузке XML в **Integrated apps**, управляет доставкой надстройки в Outlook и её аудиторией. XML `<Id>` соответствует `addinId`. Если после развёртывания видна дополнительная запись приложения в Entra, сверяйте её издателя, Application ID, Object ID и журнал создания. Одно название не устанавливает связь между объектами. В сборку вводится Client ID ручной регистрации. [Модель объектов Entra](https://learn.microsoft.com/en-us/entra/identity-platform/app-objects-and-service-principals)
4. При изменении XML откройте существующую карточку надстройки, выберите обновление файла приложения и загрузите XML с прежним `addinId` и увеличенной версией. Название в Outlook задаёт `displayName`; название регистрации меняется отдельно в Entra. При изменении только HTML/JS на прежних URL достаточно обновить файлы Worker и проверить их загрузку клиентом. [Обновление корпоративных надстроек](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/centralized-deployment-faq)

## 6. Испытать и диагностировать

| Проверка | Действие и ожидаемый результат |
| --- | --- |
| Панель и Graph | В настольном интерфейсе создания письма нажмите **Sign in**, при необходимости пройдите вход. Панель покажет профиль пилотного пользователя из `/v1.0/me`. Сверьте наличие `displayName`, почты и полей, нужных для подписи. Не копируйте ответ или токен в отчёт. |
| Событие | Создайте новое письмо после входа. Без нажатия кнопки должна появиться одна HTML-подпись с ожидаемыми именем, компанией, телефоном и почтой. Проверьте вариант с пустым необязательным полем. |
| Клиенты | Отдельно проверьте Classic Outlook на Windows, New Outlook, Outlook Web и мобильные Outlook для iOS и Android. Запишите версии, тип ящика, версию манифеста, результат входа и события. На мобильном проверяйте создание письма, кнопка Sign in там не объявлена. Сверьте поддержку сразу события и NestedAppAuth 1.1. [Поддержка NAA](https://learn.microsoft.com/en-us/javascript/api/requirement-sets/common/nested-app-auth-requirement-sets) · [События на мобильных клиентах](https://learn.microsoft.com/en-us/office/dev/add-ins/outlook/mobile-event-based) |
| Надстройка отсутствует | Проверьте tenant, почтовый ящик, группу в Integrated apps, распространение установки и поддержку клиента. |
| Ошибка входа или согласия | По коду ошибки и времени проверьте журналы входа Entra, tenant, Client ID, платформу SPA, broker URI, consent, Assignment required, группы и Conditional Access. Для `interaction_required` используйте панель в поддерживаемом клиенте. |
| Graph HTTP 401/403 | Проверьте учётную запись, делегированное User.Read, фактическое согласие и политики доступа. Панель выполняет тот же запрос профиля, что и событие. |
| Панель работает, подпись отсутствует | Проверьте непустой displayName, версию Outlook, регистрацию события, публичный JS и точное совпадение allow-list. В журналах runtime ищите `BDO: Event started`, `Signature inserted successfully` или код ошибки. Для Classic особенно важны JS-only runtime и корневой JSON. |
| Загружается прежняя версия | Сверьте публичные файлы, активную версию Worker, установленный XML, назначения и кеш клиента. Проверьте на новом письме после перезапуска. |

## 7. Откатить или удалить

1. При ошибке файлов откройте нужный Worker → **Deployments**, найдите записанную рабочую версию, выберите **… → Rollback** и проверьте ресурсы и тестовое письмо. Если версия уже недоступна, вручную опубликуйте сохранённый рабочий комплект. [Откат Cloudflare Workers](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/)
2. Если изменился манифест, восстановите согласованные параметры рабочей версии, оставьте ID установки, задайте версию выше развёрнутой и загрузите полученный XML как обновление. Согласуйте порядок переключения, чтобы URL прежнего и нового XML оставались доступны установленным клиентам во время распространения. Проверьте назначения в Microsoft 365 и Entra отдельно.
3. Для прекращения доставки снимите назначения или выберите удаление приложения в карточке **Integrated apps**. Проверьте результат на тестовом ящике после распространения. Настройки Entra и Worker имеют собственный жизненный цикл. При полном выводе из эксплуатации проверьте остальных потребителей, затем отдельно согласуйте отзыв доступа и отключение ресурсов. История исходников остаётся в GitHub.
