# REFACTORING.md — техническое задание для Codex

## 1. Цель

Реорганизовать существующий проект Outlook Graph Signature без изменения его функциональности. Получить одну кодовую базу, одну текущую ветку `main`, один механизм сборки и два независимых результата: `dist/dev/` и `dist/prod/`. Все различия сред (идентификаторы, URL, параметры авторизации, версии и прочее) подставляются автоматически из конфигурации выбранной среды. Не разворачивать приложение в рамках этой задачи.

Прочитай `AGENTS.md` и `ARCHITECTURE.md`. Действующие файлы важнее предположений в документах. Не переписывай надстройку с нуля.

## 2. Этап 1 — анализ и план (без редактирования)

1. Проверь `git status`, текущую ветку, дерево репозитория и доступные настройки npm/Node.js. Не переключай ветку, не делай reset/clean и не меняй пользовательские файлы.
2. Прочитай актуальные манифесты, HTML, исходные JS, webpack-конфиги, package.json, package-lock.json, README и gitignore. Проверь импорты, ссылки и entry points, включая desktop/mobile и старые `commands`-ресурсы.
3. Определи какие ресурсы необходимы для событийной надстройки и панели Sign in, какие являются сгенерированными, а какие относятся к действующей старой публикации. Проверь фактические URL и способы формирования `.well-known` по имеющемуся контексту.
4. Предложи конкретное дерево, карту «старый путь → новый путь», структуру конфигураций, способ генерации XML/JSON, механизм независимых сборок и план проверок. Отдельно перечисли устаревшие файлы, которые пока необходимо сохранить.
5. Если есть расхождения с заданием или требуется выбрать решение, влияющее на функциональность, задай вопрос. Не блокируй план из-за отсутствующих будущих адресов Cloudflare или PROD Client ID: их обработка предусмотрена ниже.

Остановись после плана и дождись явного разрешения на реализацию. Если владелец уже явно разрешил выполнить согласованный план, переходи к этапу 2.

## 3. Этап 2 — структура исходников

- Размести общие исходные JS в `src/`, общие HTML и иконки в `public/`, конфигурации в `config/`, единый XML-шаблон в `manifests/`, логику сборки в `scripts/`.
- Используй текущий `dev/manifest.xml` как основу XML-шаблона. Не используй старый корневой манифест как основу. Сохрани XML namespace, структуру VersionOverrides, desktop/mobile, события, требования API, разрешения, имена обработчиков и ссылки на ресурсы, изменяя только необходимое для конфигурации среды.
- Сохрани существующее поведение `graph-auth.js`, `signature-template.js`, `graph-runtime-source.js`, `signin-source.js` и HTML. В `authconfig.js` замени жёстко прописанные параметры среды на безопасно подставляемые при сборке значения. Не потеряй остальные настройки.
- Не переноси статическую тестовую подпись в новую реализацию. Если `commands.html` требуется текущему XML, оставь нейтральную совместимую страницу без подключения устаревшего JS (проверь её назначение). Не удаляй требуемую страницу или её ссылки без обоснования.
- Приведи Webpack к одному параметризованному конфигу, сохранив две независимые точки входа и два самостоятельных бандла. Старый дополнительный webpack-конфиг можно удалить после успешных проверок, если он действительно больше не нужен. Не удаляй файлы, которые обслуживает текущий GitHub Pages.
- Не меняй зависимости без необходимости; при необходимости обоснуй изменения lockfile. Добавь `dist/` в `.gitignore`, не теряя существующих правил. Обнови README.

## 4. Конфигурации сред

Используй `config/dev.json` и `config/prod.json` либо эквивалентный простой формат. Рекомендуемая схема (концептуальный пример, не готовый действующий конфиг):

```json
{
  "baseUrl": "https://signature-dev.example.invalid/",
  "clientId": "<DEV_CLIENT_ID_FROM_EXISTING_CONFIG>",
  "authority": "<AUTHORITY_FROM_EXISTING_CONFIG>",
  "addinId": "<DEV_GUID_FROM_EXISTING_MANIFEST>",
  "displayName": "BDO Auto Signature DEV",
  "manifestVersion": "1.0.0.5"
}
```

Для PROD используются соответствующие PROD-параметры, включая другой постоянный GUID и название `BDO Auto Signature`. Точное имя полей можно изменить при сохранении понятного контракта. Если есть иные действительно различающиеся параметры, вынеси их в конфигурацию; общие параметры не дублируй без необходимости.

Требования:

- DEV Client ID, tenant/authority, GUID и текущую версию брать из действующих исходников и манифеста, предварительно сверив их. Версию действующей установки не менять автоматически; при будущем обновлении XML решать вопрос повышения версии отдельно.
- PROD — отдельная регистрация Entra, отдельный GUID Outlook. Если GUID ещё нет, можно один раз сгенерировать постоянный UUID для новой PROD-надстройки и сохранить его в конфигурации (сообщить владельцу). Не генерировать GUID при каждой сборке.
- Реальных адресов Cloudflare и PROD Client ID пока нет. Не создавать Entra-регистрации и не обращаться к административным системам. Используй явные заглушки/зарезервированные `.invalid`-адреса или отдельные тестовые конфигурации. Не подставляй DEV Client ID как PROD.
- Обычные команды должны позволять проверить компиляцию обеих сред до настройки хостинга. Предпочтительный вариант: сборка с валидными по форме, но явно тестовыми значениями допустима с хорошо заметным предупреждением `NOT CONFIGURED — DO NOT DEPLOY`; это не готовый релиз. Если выбран строгий отказ при отсутствующих значениях, предусмотрена документированная локальная проверка обеих сборок на фиктивной конфигурации. Не ослабляй валидацию реальных параметров.
- Не хранить секреты. Проверять формат UUID, HTTPS baseUrl (без query/fragment), четырёхкомпонентную версию манифеста и необходимые параметры. Корректно обрабатывать завершающий `/` и возможный подкаталог в URL. Не строить URL с помощью `path.join`.
- Путь вывода лучше вычислять внутри сборщика строго из разрешённого target (`dev` или `prod`), а не принимать произвольный путь для удаления из JSON. Если используется `outputDir`, валидировать, что он точно соответствует `dist/<target>` внутри репозитория. Не путать `baseUrl` и путь вывода.

## 5. Генерация ресурсов

Реализуй выбор окружения через команды:

```bash
npm run build:dev
npm run build:prod
npm run build:all
```

Последняя команда последовательно запускает обе независимые сборки. Не добавляй автоматическую публикацию или отдельную постоянную ветку. Не требуй локальный HTTPS-сервер для компиляции.

Ожидаемый процесс:

```text
выбранный target
  → чтение и валидация конфигурации
  → компиляция общего JS с параметрами среды
  → копирование общих HTML/PNG
  → генерация XML из общего шаблона
  → генерация .well-known JSON
  → проверка результата
  → размещение в dist/<target>
```

- Webpack должен формировать `graph-runtime.js` и `signin.js` с текущими возможностями оптимизации. В оба бандла подставляются соответствующие Client ID и authority. Никаких зависимостей от отдельного файла конфигурации на сайте, если они уже включены при сборке. Используй безопасную подстановку JS-строк (например, DefinePlugin + JSON.stringify), не конкатенацию непроверенного кода.
- Используй общий XML-шаблон. Автоматически подставляй GUID, DisplayName, версию и все относящиеся к среде URL, в том числе иконки, HTML, JS, SupportUrl, FormSettings, Resources/AppDomains и другие фактически имеющиеся элементы. Различай полный baseUrl с путём и origin, если конкретное XML-поле требует origin. Не изменяй namespace URL или внешние ссылки Microsoft, которые не относятся к адресу приложения. Корректно экранируй XML-значения; проверь отсутствие неразрешённых шаблонных маркеров.
- Сохрани относительные ссылки HTML на JS внутри комплекта. Не изменяй URL CDN Office.js без необходимости.
- Сгенерируй `dist/<target>/.well-known/microsoft-officeaddins-allowed.json` с `allowed` массивом, содержащим точный публичный URL `graph-runtime.js` из соответствующего XML. Для будущих независимых сайтов этот каталог попадёт в корень origin. При изменении baseUrl XML и JSON должны меняться согласованно.
- Выбранная сборка не должна изменять другую папку или опубликованный `dev/`. Желательно собирать во временную папку и заменять выбранный выход только после успешной компиляции и проверок, чтобы при сбое сохранить предыдущую рабочую сборку. Безопасно ограничь любые удаления только собственными временными/выходными директориями. При ошибке — ненулевой exit code.
- Сохраняй нужные лицензии и другие необходимые выходные файлы. Печатай target, путь результата, степень готовности конфигурации и ошибки. Не печатай токены и реальные профили пользователей.

## 6. Сохранение действующей публикации

Текущий GitHub Pages нельзя ломать рефакторингом. Сохрани опубликованные файлы `dev/` и старые корневые ресурсы (в том числе иконки), действующий `dev/manifest.xml`, а также отдельный репозиторий корня домена. Перенос исходников выполняй с сохранением старых опубликованных путей: сначала копирование, затем очистка только тех непубликуемых файлов, безопасность удаления которых доказана и согласована. Допустимо временное дублирование legacy-файлов; это не вторая кодовая база для дальнейшей разработки.

В README явно укажи, что новые сборки создаются в `dist/`, а прежние публикационные файлы заморожены до миграции. Не изменяй конфигурацию GitHub Pages, не делай `git push`, не публикуй в Cloudflare, не загружай манифесты в Microsoft 365.

## 7. Проверки и критерии приёмки

Выполни проверки после согласованной реализации; по возможности автоматизируй их средствами Node.js без тяжёлых новых зависимостей. Если зависимости недоступны, зафиксируй блокер вместо утверждения об успешной сборке.

| Проверка | Ожидаемый результат |
| --- | --- |
| `npm ci` (если требуется, с разрешённым сетевым доступом) | Установка по lockfile без непредусмотренных обновлений зависимостей |
| `npm run build:dev` | Формируется полный `dist/dev/` |
| `npm run build:prod` | Формируется полный `dist/prod/` либо явно документированный тестовый режим при незаданных параметрах |
| `npm run build:all` | Обе сборки последовательно создаются корректно |
| Независимость | Сравнить SHA-256 и перечень файлов PROD до/после DEV и наоборот; ничего в другой среде не изменилось |
| Конфигурация JS | Оба бандла каждой среды содержат ожидаемые настройки авторизации; нет подстановок другой среды или неразрешённых маркеров |
| XML | Синтаксически корректный XML, сохранены события и разрешения; правильные GUID, версия, название и URL; все локальные ресурсы присутствуют |
| JSON | Корректный `.well-known`, URL точно соответствует событийному JS из XML |
| Single-chunk | Каждый entry создаёт один необходимый самостоятельный JS-бандл, без дополнительных JS-зависимостей для запуска |
| Неверный target / конфигурация | Понятная ошибка, ненулевой exit code, чужая папка и действующая публикация не затронуты |
| Бизнес-логика | Сопоставление исходников до/после и минимальные офлайн-проверки генератора подписи на фиктивных данных; неизменный результат |
| Текущая публикация | Проверить diff/контрольные суммы legacy-ресурсов; изменения опубликованного содержимого отсутствуют |
| Git | `dist/` игнорируется; нет новых коммитов, push и развёртываний |

По возможности выполнить официальный валидатор Office Add-in manifest, если он доступен без нежелательных изменений зависимостей. Если валидатор не может проверить URL до публикации или сеть недоступна, разделить локальную XML-валидацию и проверку доступности URL. Не считать эти проверки подтверждением работоспособности в Outlook.

## 8. После рефакторинга (не входит в текущую реализацию)

Владелец отдельно создаст два Cloudflare Pages проекта и определит реальные публичные адреса. Будет создана/настроена PROD-регистрация Entra и проверены redirect URI, доступ пользователей, разрешения и admin consent. Затем необходимо собрать DEV с реальными параметрами, вручную опубликовать содержимое его папки, проверить реальные HTTPS URL, `.well-known` в корне origin, поведение редиректов HTML и доступность ресурсов. При необходимости повысить версию/обновить установленный XML. Проверить авторизацию, новую подпись и панель Sign in в Classic, New, Web и Mobile Outlook. Только после этого собрать PROD из того же проверенного состояния исходников и выполнить отдельную ручную публикацию. Старые опубликованные ресурсы можно убирать только после подтверждения миграции и отсутствия старых установок.

## 9. Итоговый отчёт

В конце предоставь:

- Целевое дерево и перечень изменённых, созданных и удалённых файлов, включая причины удаления.
- Объяснение механизма сборки: какой файл откуда берётся, где хранятся конфиги, как подставляются URL и параметры авторизации, что создаёт Webpack и что создаёт скрипт.
- Команды запуска, результаты проверок, сведения о предупреждениях и ограничениях. Укажи отдельно, проверялась ли реальная работа Outlook (в рамках этой задачи — обычно нет).
- Список ещё не настроенных полей DEV/PROD и конкретные действия владельца при миграции. Не выдавай сборку с заглушками за релиз.
- `git status` и краткое описание diff. Не добавляй изменения в индекс, не коммить и не пушь.
