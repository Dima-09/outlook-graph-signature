# REFACTORING.md — состояние рефакторинга и миграция

Документ фиксирует результат структурного рефакторинга и оставшиеся шаги перехода
на новый хостинг. Это не задание повторно переносить исходники или переписывать
сборщик. Текущее устройство описано в [ARCHITECTURE.md](ARCHITECTURE.md), команды
и настройки — в [README.md](README.md), правила работы — в [AGENTS.md](AGENTS.md).

## Реализовано в репозитории

- Общие исходники находятся в `src/`, HTML и иконки — в `public/`.
- DEV и PROD используют отдельные JSON-конфигурации и единый XML-шаблон.
- Один параметризованный Webpack-конфиг и `scripts/build.cjs` формируют
  независимые комплекты `dist/dev/` и `dist/prod/` из ветки `main`.
- Идентификаторы, URL и остальные параметры среды подставляются при сборке.
  Сохранены `configured`, валидация и предупреждение о незавершённой настройке.
- Реализованы отдельные самостоятельные бандлы runtime и Sign in, генерация
  `.well-known`, проверка комплекта, блокировки и замена выбранного результата.
- Сборка отделена от публикации; прежние файлы GitHub Pages сохранены.
- Есть офлайн-тесты сборщика и сравнения с прежней реализацией на фиктивных данных.

Эти пункты подтверждены чтением файлов, а не новым прогоном сборок или проверкой
установленной надстройки. Историческое сообщение об успешной работе старой публикации
не является подтверждением работы новых комплектов на Cloudflare.

## Текущее состояние и ограничения

| Область | Состояние |
| --- | --- |
| DEV | В конфигурации указан URL `workers.dev`, но `configured: false`; доступность и работа публикации не подтверждены этим аудитом |
| PROD | `configured: false`, URL и параметры Entra содержат заглушки; отдельный GUID надстройки уже сохранён |
| Новый хостинг | Выбран Cloudflare Workers Static Assets: два отдельных Workers, только статические файлы |
| Публикация | Ручная; Wrangler, Cloudflare API, GitHub-интеграция и автоматическая публикация не используются |
| GitHub Pages | Обслуживает старую корпоративную надстройку до полного перехода PROD |
| Тесты | Зависимы от старых файлов и начальных настроек; найдено устаревшее ожидание ошибки для `configured: true` в DEV |
| Реальная среда | Настройки Entra, права, HTTPS-ресурсы и Outlook требуют отдельной проверки |

Описание расхождения в тесте приведено в [README.md](README.md). В рамках
рефакторинга документации тесты, конфигурации и механизм валидации не меняются.
Отсутствующие реальные параметры нельзя заменять вымышленными рабочими значениями.

## Оставшиеся шаги миграции

Ниже — будущие действия владельца или отдельные согласованные задачи.
Наличие этого списка не разрешает агенту публикацию или изменение внешних систем.

1. Подтвердить отдельные Workers Static Assets и HTTPS origin для DEV и PROD.
   Использовать их только для статических файлов, без серверной логики Worker.
   Сохранить независимость приложения от конкретного хостинга.
2. Подготовить реальные параметры каждой среды. Для PROD настроить отдельную
   регистрацию Entra, проверить redirect URI для NAA, доступ пользователей,
   разрешения и admin consent. Согласовать постоянные GUID надстроек и версии
   манифестов. Не генерировать GUID при каждой сборке и не создавать Client Secret.
3. Отдельно актуализировать тесты, привязанные к начальной конфигурации и старым
   файлам, сохранив содержательные проверки валидации и поведения подписи.
   Внести реальные параметры в конфигурации; `configured: true` ставить после
   завершения настройки. Флаг сам по себе не подтверждает успешное развёртывание.
4. Собрать DEV, выполнить локальные проверки, вручную опубликовать содержимое
   `dist/dev/` в корень выбранного DEV origin. Проверить, что `.well-known`
   также попал на хостинг. Публикация не должна запускаться сборщиком.
5. Проверить по публичным HTTPS URL манифест, HTML, JS, иконки и JSON:
   содержимое, типы ответов и редиректы должны соответствовать ожидаемым ресурсам.
   Особое внимание — точным URL HTML из манифеста, отсутствию подмены JS/JSON
   HTML-страницей и совпадению `allowed` с URL событийного JS.
6. Обновить установленный DEV-манифест с согласованной версией. Проверить
   авторизацию и автоматическую подпись в Classic, New, Web и Mobile Outlook;
   панель Sign in — в клиентах, где её команда предусмотрена манифестом.
   Зафиксировать версии клиентов, результаты и ограничения, не предполагая
   поддержку только на основании XML.
7. После успешной проверки DEV собрать PROD из того же проверенного состояния
   общих исходников, отдельно опубликовать и проверить PROD. Завершить переход
   корпоративных установок, подтвердить отсутствие зависимости от старых URL.
8. Только после успешного тестирования и полного перехода PROD запросить
   отдельное указание владельца на удаление старой инфраструктуры.

Подробные действия в интерфейсе Cloudflare и фактическое поведение ручной загрузки
в этой задаче не проверялись. Новые сервисы, инструменты и автоматизация не подключались.

## Критерии приёмки сборок и миграции

Это перечень необходимых проверок для отдельного этапа приёмки, а не отчёт
об их успешном выполнении при обновлении документации.

| Проверка | Требуемое свидетельство |
| --- | --- |
| Реальные сборки | Успешные `build:dev`, `build:prod`, `build:all`; предупреждения и готовность конфигурации зафиксированы |
| Офлайн-тесты | Результаты `npm test` после согласованной актуализации устаревших ожиданий |
| Изоляция | Перечни файлов и SHA-256 PROD до/после DEV и наоборот совпадают |
| JS | В каждой среде два самостоятельных бандла с нужными Client ID и authority, без дополнительных необходимых JS-чанков |
| XML | Корректный синтаксис, ожидаемые GUID, версия, название, URL, сохранённые события и разрешения; отдельно результат проверки схемы Office Add-in, если выполнялась |
| HTML и ресурсы | Все необходимые файлы присутствуют, относительные ссылки ведут к соответствующим бандлам |
| `.well-known` | Валидный JSON, точный URL событийного JS, доступность в корне origin после публикации |
| Ошибки сборки | Ненулевой код при неверных параметрах; прежние результаты и другая среда сохранены |
| Прежняя публикация | Старый `dev/` и корневые ресурсы не изменены; GitHub Pages продолжает обслуживать прежние установки |
| Реальная среда | Отдельные результаты проверки DEV и PROD, Entra/NAA и поддерживаемых клиентов Outlook |

Установка зависимостей при необходимости выполняется по lockfile с разрешённым
сетевым доступом. Не следует добавлять инструменты ради проверки без необходимости
и согласования. Локальный разбор XML не заменяет валидацию схемы, проверка схемы
не заменяет доступность URL, а сборка и офлайн-тесты не заменяют работу Outlook.

## Очистка после полного перехода PROD

До отдельного указания владельца ничего из перечисленного не удаляется и не перемещается.

| Кандидат | Причина и условия удаления |
| --- | --- |
| `dev/` целиком, включая исходники, бандлы, HTML, манифест и лицензии | Замороженная старая публикация; удаление после прекращения использования старых URL и замены контрольных зависимостей тестов |
| Корневые `manifest.xml`, `commands.html`, `commands.js` | Первоначальная реализация; удалить после проверки старых корпоративных установок |
| Корневые `icon-16.png`, `icon-32.png`, `icon-80.png` | Старые публичные ресурсы; новые сборки используют `public/`, но старые манифесты и тесты ещё зависят от корневых файлов |
| Публикация GitHub Pages этого проекта | Вывод из эксплуатации после подтверждения полного перехода PROD и отсутствия потребителей старых адресов |
| Связанные ресурсы корня домена GitHub Pages | По прежнему контексту `.well-known` размещён в отдельном репозитории `Dima-09/Dima-09.github.io`; проверить остальных потребителей домена до удаления связанных записей или отключения инфраструктуры |

Отдельный репозиторий домена не входит в текущую рабочую область и не проверялся.
Его целиком нельзя считать ненужным по состоянию этого проекта.
`public/commands.html` не является кандидатом на удаление: он нужен текущему шаблону.
Контрольные legacy-файлы в тестах нельзя удалить без отдельного пересмотра тестов.

`webpack-cli` остаётся devDependency, хотя команды проекта используют Node API Webpack.
Его необходимость можно оценить отдельно; это не условие миграции и не разрешение
менять зависимости или lockfile в рамках документационной задачи.
